# 真实经验复用基准方案

`pel demo` 是确定性离线验收。本方案用于下一轮真实代理验证，不能把两者混为一项效果证明。

## 对照设计

选择 PRD 的三个领域：研究、课程 / 算法、性能优化。每个领域准备过去任务 A 和相关的新任务 B，以及与 B 无关的历史作为检索干扰项。A 应至少包含一条已确认失败、一个可复用产物和一个合理评估器。

固定代理、模型、模型参数、工作环境、B 的初始代码 / 数据与预算。分别在隔离的工作目录运行：

1. 无历史经验：直接启动原生代理执行任务 B。
2. 有历史经验：导入 A，使用 `pel run` 执行同一个 B。

不要使用第一次 B 修改后的代码作为第二次 B 的起点。多次重复、交替顺序，保留失败结果，不把效果仅归因于一次更快的运行。

## 记录字段

| 指标 | 实际记录方式 |
| --- | --- |
| 人工重复说明 | 从用户消息统计为解释旧状态 / 决策而增加的轮次 |
| 重复已知失败 | 从工具轨迹核对是否再次执行相同失败方法，以及当时条件是否一致 |
| 产物复用 | 比较已有脚本 / 数据是否被采用，是否重新创建相同产物 |
| 达到可用结果的时间 / 轮次 | 用真实进程时间与完整消息数，失败任务单列 |
| 评估器采用 | 检查是否执行正确 oracle / benchmark；成功不仅凭代理声明 |
| 检索精度 | 人工标注实际注入的 `selected_ids`，相关数 / 注入数 |
| 有害 / 过期影响 | 记录历史陈述导致的错误操作、过期状态和撤回经验 |
| Experience Reuse Rate | 记录历史是否实际改变有用行为，不把“有注入”视为“有复用” |

通过 `pel inspect` 检查来源；通过 `pel export` 保存经验、证据、编译选择与生命周期；保留对应代理 JSONL 和实际评估结果。

将新结果以 `pel feedback <id> --action strengthen|weaken|correct --reason ...` 回写。对支持某条经验的结果，应指明具体工作负载、命令、输出与条件；对反例应缩小范围或标记争议。

## 通过条件

- 同一个代理在任务 B 中确实避免至少一次重复说明、已知失败或重复发现。
- 采用的经验与 B 的项目 / 领域 / 条件相符，来源可追踪。
- 已撤回、过期和不相关经验不会被当成当前事实注入。
- 新结果改变了经验生命周期，并在第三次检索中得到反映。
- 提取准确性与检索精度达标后，再扩大输入来源或接入 LLM 提取。
